# Pi 5 JACK buffer — 64×2 in daily use, ear-only (2026-08-27)

*Last updated: 2026-08-27 (America/Toronto)*

**Status:** **Provisional.** Supersedes the buffer finding in
[`PI5-SESSION-CLOSEOUT-2026-08-23.md`](PI5-SESSION-CLOSEOUT-2026-08-23.md) §Configuration locked.
**No instrumented evidence exists for this setting.**

---

## Claim

The Pi 5 reference unit has been running **`MPE_JACK_BUFFER=64`, `MPE_JACK_PERIODS=2`
@ 48 kHz** as the daily player setting. It is the buffer the operator tests on.

## Evidence

**Ear only.** Playing sessions on the reference unit, no audible crackle or dropout
reported. That is the whole of it.

| Not measured | Why it matters |
|---|---|
| **xrun count over a defined window** | The failure this setting is most likely to have; ear catches gross dropouts, not sparse xruns |
| **Voice count at which it degrades** | 128×2 was characterised at 24 voices ([`pi5-irq-phase1-2026-08-23.md`](pi5-irq-phase1-2026-08-23.md)); 64×2 has no equivalent |
| **Soak duration** | No 10-min-plus run under load |
| **Patch coverage** | "Most patches" is operator recollection, not a set |
| **Round-trip latency** | 64×2 @ 48 kHz is **2.67 ms of JACK buffering**, *not* end-to-end latency — USB MIDI in and DAC out are unmeasured |

## What this supersedes, and what is now unexplained

The 2026-08-23 closeout recorded that **64×2 broke ALSA/USB** on this board
(§Configuration locked, §Ear check). That collapse is no longer reproducing.

**The cause of the original collapse was never diagnosed, and neither was its
disappearance.** Candidate differences between then and now — none confirmed:

- `-mcpu=cortex-a76` Surge build (`0ac9456c…`, commit `253f8d86`) replaced the generic
  binary on 2026-08-24, *after* the collapse was observed
- IRQ/affinity and hygiene changes landed across the same window
- PSU: the 08-23 session ran a 5 V / 3 A supply, below the 27 W / 5 A spec
- USB audio device or port differences between sessions

Until one of these is identified, **64×2 should be treated as working on the reference
unit, not as a platform claim.** A second unit may still collapse the way this one did.

## What would close this

1. xrun count over a 10-minute soak at 64×2 under `midi-load-hold`, matched against the
   existing 128×2 run, on the spec PSU with active cooling.
2. A voice-count sweep to find where 64×2 degrades.
3. One deliberate attempt to *reproduce* the original ALSA/USB collapse — if it cannot be
   reproduced on the old binary, that isolates the cause.

Until then no buffer or latency figure from this unit should appear in external material
(README claims, launch copy, SR&ED evidence) without the words **ear-validated,
uninstrumented** attached.
